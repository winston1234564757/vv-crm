# Розділення готівки й безготівки

**Дата:** 2026-07-28
**Статус:** дизайн погоджено, план реалізації ще не написано

## Проблема

Безготівка в системі невідрізнима від готівки.

1. **Спосіб оплати знає лише POS.** `payment_splits.method` (`cash` / `card` / `transfer`)
   заповнюється тільки при продажу. `pay_repair` і аванс за замовлення приймають
   лише касу й суму — способу оплати там немає взагалі. З 25 останніх надходжень
   11 не мають його зафіксованим.

2. **Картка лягає в касу разом із готівкою.** POS обирає касу за категорією
   товару незалежно від методу, тож гроші з термінала потрапляють туди ж, де
   фізична готівка, і далі діляться по сейфах тими самими відсотками.

Наслідок, зафіксований 2026-07-28: продаж на 1300 карткою потрапив у «Касу
аксесуарів» і розійшовся як 852 OPEX / 639 Growth / 639 ЧП, хоча цих грошей у
шухляді ніколи не було.

## Рішення власника

| Питання | Рішення |
|---|---|
| Куди йде безготівка | Окремий рахунок, розподіл вручну — як зараз із касами |
| Скільки рахунків | Один на все (не по категоріях) |
| Історія | Усе без позначки = готівка; сьогоднішні 1300 перенести на рахунок |
| Як ловити метод для ремонтів і авансів | Дві кнопки «Готівка / Картка» замість вибору каси |
| Де показувати розбивку | Фінанси, «Гроші в наявності», «Продажі сьогодні», звіти й список продажів |
| Глибина розділення | Загальна по системі; розріз по кожному сейфу — **ні** |

## Модель даних

Новий рядок у `cash_registers`:

```
name = 'Безготівка', type = 'cashless', balance = 0
```

Жодних нових таблиць. `transactions` не змінюється: `to_type = 'cash_register'`
працює для рахунку так само, як для кас. Нової колонки «метод» на транзакціях
не буде — **спосіб оплати визначається тим, у який контейнер лягли гроші**.

Наслідок, який робить міграцію історії непотрібною: уся наявна історія лежить у
трьох касах, тобто автоматично читається як готівка. Це відповідає дійсності —
каса сходиться.

`payment_splits.method` лишається як є: він потрібен для звітності по чеках
(«скільки сьогодні пробили карткою»), але вже не керує тим, куди йдуть гроші.

## Потік грошей

Інваріант:

> `method = 'cash'` → каса за категорією товару.
> Будь-який інший метод → «Безготівка».

**Продаж (`createMultiSaleAction`, `sales.ts:300`).** Цільова каса стає функцією
методу, а не лише категорії. Зараз категорія обирає касу беззастережно — саме
тут 1300 і загубились.

**Оплата ремонту (`pay_repair`) і аванс за замовлення.** Сигнатура RPC не
змінюється — вона вже приймає `p_cash_register_id`. Змінюється інтерфейс: замість
списку кас дві кнопки, які підставляють або касу за контекстом, або рахунок
безготівки. Кліків не більшає.

**Розподіл.** «Безготівка» стає ще одним пунктом у кнопці «Розподіл». Відсотків
для неї в налаштуваннях немає (там лише tech / accessories / repairs), тож
модалка відкривається з нулями — суми вписуються руками. Це відповідає вибраному
ручному режиму.

**Витрати не змінюються.** Параметр методу на витраті був би потрібен лише для
розрізу по кожному сейфу, від якого відмовились.

## «Готівка» більше не дорівнює «сумі кас»

Головна ціна цього підходу. Місць, які рахують готівку, рівно чотири:

| Файл | Що рахує |
|---|---|
| `lib/data-dashboard.ts:397` | `cashTotal` — картка «Гроші в наявності» |
| `lib/data-finance.ts` (×2) | каси на екрані фінансів і в звіті |
| `app/api/ai-chat/route.ts` | контекст фінансового копілота |

Правило **не розкидається** по цих чотирьох місцях. Один хелпер у `lib/finance`:

```ts
splitByKind(registers) -> { cash, cashless, total }
```

Причина саме така: у цьому проєкті вже є слід від скопійованого правила —
`EARNED_REPAIR_STATUSES` колись розійшовся по незалежних копіях і почав означати
різне в різних місцях.

## Виправлення сьогоднішніх 1300

Три перекази через наявний `transfer_funds` (`safe → cash_register`), кожен з
описом-поясненням. Балансів руками не чіпаємо — RPC пише рядки в реєстр і
оновлює баланси атомарно, тож корекція лишає слід.

| | Зараз | Стане | Рух |
|---|---:|---:|---:|
| Безготівка | 0 | 1300 | +1300 |
| OPEX | 4752 | 4232 | −520 |
| Growth | 2799 | 2409 | −390 |
| Чистий прибуток | 2579 | 2189 | −390 |
| **Разом** | 10130 | 10130 | 0 |

Розрахунок: каса аксесуарів отримала 2130 (830 готівкою + 1300 карткою) і роздала
їх як 852 / 639 / 639. За новим правилом розподілу підлягали лише 830 готівкою →
332 / 249 / 249. Різниця по кожному сейфу і повертається на рахунок.

## Інтерфейс

**Фінанси → «Розподіл ліквідності».** Четверта картка «Безготівка» поруч із
касами, візуально відокремлена — це не каса. Над рядком підсумок у три числа:
`Готівкою • Карткою • Разом`.

Дрібниця, яку легко проґавити: колірна мапа кас (`crColors` у
`app/admin/finance/page.tsx`) має ключі лише `tech` / `accessories` / `repairs`.
Для `cashless` потрібен власний запис, інакше картка мовчки візьме запасний
колір і зіллється з рештою.

**Дашборд → «Гроші в наявності».** Головна цифра (разом) і два дрібні рядки під
нею. Верстку не ламає: у картці вже є місце під `runway` і `dailyOpex`.

**Дашборд → «Продажі сьогодні».** Виторг за день розбитий за методом. Джерело —
`payment_splits` тих чеків, що вже вантажаться для списку.

Картка охоплює **лише продажі**, як і зараз. Оплати ремонтів і аванси за
замовлення в неї не входять, хоча теж можуть бути карткою — вони живуть в інших
картках дашборду. Отже сума «карткою» тут ≠ усе, що сьогодні прийшло на карту;
повна картина — у балансі рахунку «Безготівка».

**Звіти й список продажів.** Колонка методу в таблиці чеків, підсумки за
методами у звітах.

## Межі рішення

Це свідомі обмеження, а не недоробки.

**Розділення живе до розподілу.** «Безготівка» тримає картку окремо, поки її не
розподілили. Після розподілу гроші йдуть у сейфи й змішуються з готівковими —
сейф не знає, звідки в ньому сума. Тобто «на карті» показує **нерозподілену**
безготівку, а не всі гроші, що колись прийшли карткою.

Це прийнято усвідомлено: розділення потрібне для звірки шухляди й розуміння,
скільки прийшло на карту — обидва завдання стосуються нерозподіленого.

**Альтернатива, від якої відмовились:** два лічильники (`balance_cash`,
`balance_cashless`) на кожному сейфі з `CHECK (balance = balance_cash +
balance_cashless)`. Дало б точний розріз у будь-який момент, але вимагало б
переписати одинадцять функцій, що торкаються сейфів (`distribute_register_funds`,
`transfer_funds`, `create_expense`, `top_up_safe`, `withdraw_owner_share`,
`purchase_inventory_item`, `pay_purchase_atomic`, `register_device_purchase`,
`register_part_purchase`, `handle_inventory_item_deletion`, `delete_transaction`)
і додати вибір методу в чотири форми назавжди.

## Ризики

**Забута каса в старому коді.** Будь-яке місце, що підсумовує `cash_registers`
без фільтра, після зміни мовчки зарахує картку в готівку. Хелпер `splitByKind`
знижує ризик, але не прибирає: нові місця можуть звернутись до таблиці напряму.
Пом'якшення — тест, який ловить прямі звернення в обхід хелпера.

**Розподіл «Безготівки» без відсотків.** Модалка відкриється з нулями, і сума
має зійтись руками. Якщо власник введе менше за баланс — залишок просто лишиться
на рахунку; це не помилка, а часткове зняття.

**Метод `transfer`.** POS уже вміє третій метод («Переказ»), і за інваріантом він
теж піде в «Безготівку». Це правильно — переказ не потрапляє в шухляду.

## Тести

- `splitByKind` — розділяє каси за типом; порожній список дає нулі; рахунок без
  кас дає `cash = 0`.
- Інваріант маршрутизації: `cash` → каса категорії, `card` і `transfer` →
  рахунок безготівки, для всіх трьох категорій товару.
- Корекція 1300: після трьох переказів сума всіх контейнерів незмінна.
- Регресія на «готівку»: `cashTotal` не включає рахунок безготівки.
