# Розширені характеристики аксесуарів живлення

**Дата:** 2026-08-09
**Статус:** затверджено до реалізації (після грилінгу)

## Задача

На складі 66 позицій аксесуарів, з них 33 — живлення: 18 кабелів, 14 зарядних
пристроїв, 1 павербанк. Усі суттєві характеристики — розʼєм, потужність,
комплектність — закодовані текстом усередині `accessories.name`:

```
Кабель Hoco X96 Hyper Type-C to Type-C 100W (1m)
МЗП Borofone BA97A PD30W (1USB-C)
МЗП Hoco CS93A Leader PD20W (1USB-C) + кабель Type-C to Type-C
```

Через це на питання «скільки лишилось саме Type-C→Type-C» і «скільки блоків на
30 Вт» відповіді немає: фільтр працює лише по категорії (`cable`, `charger`, …),
пошук — підрядком по назві. Продавець за прилавком читає 18 назв очима.

Треба структуровані характеристики: заводяться напівавтоматично, показуються
фасетними фільтрами із залишками на складі та в касі, і текстовим рядком —
на вітрині.

## Обсяг

**Входить:** категорії `cable`, `charger`, `powerbank`.

**Місця:** форма товару, CSV-імпорт, сторінка «Аксесуари», POS, вітрина `/shop`.

**Не входить:**
- решта 5 категорій (`case`, `screen_protector`, `headphones`, `speaker`, `other`)
  — форма для них не змінюється. У `other` товарів живлення немає (перевірено:
  автотримач, BT-ресивер, скло на Redmi Watch);
- окремий екран-зведення по залишках;
- фільтр по довжині кабеля — довжина тільки показується (три значення на 18
  кабелів не варті ще одного ряду чипсів);
- кабелі 3-в-1 — модель «звідки → куди» їх не виражає; такого товару немає
  і не планується.

## Модель даних

Одна колонка `specs jsonb` на `accessories` (nullable). Чому не окремі колонки:
`database.ts` у цьому проєкті не регенерується, тип пишемо руками в обох випадках;
даних 66 рядків, індекси не потрібні; а комплект «блок + кабель в одному SKU» у
колонковій схемі дав би два майже дублюючі набори полів.

```ts
// src/lib/accessory-specs.ts
type Connector = "usb_a" | "usb_c" | "lightning" | "micro_usb" | "other";
type Port      = "usb_a" | "usb_c";           // вихід блока/павербанка
type Protocol  = "pd" | "qc3";

type CableSpec = {
  from: Connector;      // обовʼязково
  to: Connector;        // обовʼязково
  watts?: number;       // як на коробці
  amps?: number;        // як на коробці
  length_m?: number;
};

type ChargerSpec = {
  watts?: number;
  protocols: Protocol[];
  ports: Port[];        // перелік типів без кількості
};

type PowerbankSpec = {
  mah?: number;
  watts?: number;
  wireless: boolean;
  ports: Port[];
};

type PowerSpec = {
  cable?: CableSpec;
  charger?: ChargerSpec;
  powerbank?: PowerbankSpec;
};
```

**Комплект не має власного типу.** Комплект — це запис, де присутні одночасно
`charger` (або `powerbank`) і `cable`. Тому набір полів кабеля один на всі випадки,
без дублювання.

Вати й ампери — два незалежні необовʼязкові поля; заповнюється те, що надруковане
на упаковці. Ніяких перерахунків 2.4A → 12Вт: цифра в картці має збігатися з тим,
що клієнт бачить на коробці.

Порти — перелік типів без кількості: `["usb_a", "usb_c"]`. Наслідок, прийнятий
свідомо: блок з двома USB-A не відрізнити від блока з одним.

`Connector` має значення `other` — щоб кабель, якого немає в списку (USB→AUX
тощо), можна було завести, не ламаючи обовʼязковість розʼємів.

### Валідація

`specs` розбирається zod-схемою (zod 4 вже в залежностях) на кожному записі.
Без цього друкарська помилка в ключі jsonb пройде мовчки, а товар просто зникне
з фасета — помилка, яку майже неможливо помітити.

Правила:
- `cable.from` / `cable.to` — **обовʼязкові**, якщо блок `cable` присутній.
  Кабель без розʼємів невидимий для всієї фічі, тож збереження блокується;
- `charger.ports`, `powerbank.ports` — масиви без дублікатів, **можуть бути порожні**
  (на коробці портів може не бути вказано — вигадувати нема з чого);
- числові поля — додатні; порожній рядок із форми стає `undefined`, а не `0`;
- порожній `PowerSpec` (жодного блока) зберігається як `null`, не як `{}`.

### Міграція

```sql
alter table accessories add column specs jsonb;
```

`database.ts` не регенеруємо — тип додається вручну до інтерфейсу рядка
`accessories`, доступ у місцях, де згенерований тип не знає про колонку, через
`as any` (усталена практика проєкту). Файл міграції в `docs/migrations/`
перейменувати під ту версію, яку `apply_migration` реально запише в прод.

## Розбір назв

Парсер — центральна частина фічі, а не разовий скрипт для заливки. Назви від
постачальника дисципліновані, тож розбір покриває майже все, а ручне заповнення
залишається як виправлення, а не як основна робота. Без цього фіча тихо гниє:
+5 полів на товар при заведенні партіями означає, що через три місяці половина
каталогу — «Без характеристик», і чипси починають брехати не «немає Type-C→Type-C»,
а «не заповнено».

Правила:
- `USB to X` → `from: usb_a`; `Type-C to X` → `from: usb_c`;
- `MicroUSB` → `micro_usb`, `Type-C` → `usb_c`, `Lightning` → `lightning`;
- `\d+(\.\d+)?W` → `watts`, `\d+(\.\d+)?A` → `amps`, `\((\d+(\.\d+)?)m\)` → `length_m`;
- `PD` → протокол `pd`, `QC3.0` → `qc3`;
- `(1USB-A/1C)` → `["usb_a","usb_c"]`, `(1USB-C)` → `["usb_c"]`, `(1USB-A)` → `["usb_a"]`;
- `+ кабель X to Y` у назві блока → блок `cable` із тими самими правилами;
- `з БЗП` → `wireless: true`, `\d+ mAh` → `mah`.

**Коли спрацьовує:**

| Місце | Поведінка |
|---|---|
| Створення товару | заповнює всі розібрані поля; значення позначені як «розібрано з назви», користувач правит |
| CSV-імпорт | те саме; у прев'ю імпорту зʼявляється колонка «Характеристики» — видно, що розібралось, ще до заливки |
| Редагування товару | заповнює **тільки порожні** поля, ніколи не чіпає заповнені |

Правило редагування захищає ручні правки: якщо ти виправив `100W` на `60W`, бо
назва від постачальника бреше, то подальша правка назви не поверне 100 тихцем.

**Часткове розібрання — норма.** Розібрав розʼєми, не розібрав довжину — заповнює
розʼєми, довжину лишає порожньою. «Все або нічого» викидає корисне разом із
незрозумілим.

Парсер живе в `src/lib/accessory-specs.ts` (не в `scripts/`): він потрібен у
формі, в імпорті й у разовій заливці, тобто це продуктовий код.

## Форма товару

У `AccessoryForm` додається секція «Характеристики», видима залежно від обраної
категорії:

| Категорія | Поля |
|---|---|
| Кабель | Звідки → Куди (2 селекти, обовʼязкові), Вт, A, довжина (м) |
| Зарядний пристрій | Вт, протоколи (чекбокси PD / QC3.0), порти (чекбокси USB-A / USB-C), тумблер «У комплекті кабель» → розкриває поля кабеля |
| Павербанк | mAh, Вт, БЗП (чекбокс), порти, той самий тумблер |
| решта | секція не показується |

Перемикання категорії в селекті перемальовує секцію без втрати вже введених
значень інших блоків (стан секції живе в React, у formData їде лише актуальне).

Поля виносяться в окремий компонент `src/components/forms/AccessorySpecFields.tsx` —
`AccessoryForm` уже 200 рядків, вбудовування трьох наборів полів зробило б його
нечитним.

## Фільтри

Другий ряд чипсів під наявним рядом категорій, на **сторінці «Аксесуари» і в POS**.
Показується лише коли обрано категорію живлення. Бейдж на чипсі — **штуки**
(`sum(stock)`), не позиції: питання було «скільки залишилось».

**Кабелі** — чипси по парах розʼємів, зібрані з наявних даних:

```
[USB-A→Type-C 5 шт] [Type-C→Type-C 7 шт] [USB-A→microUSB 6 шт] [Type-C→Lightning 4 шт]
```

**Блоки** — два ряди:

```
Потужність:   [18W 3] [20W 6] [22.5W 2] [30W 7]
Комплект:     [Тільки блок 11] [+ Type-C→Type-C 4] [+ Type-C→Lightning 2] [+ USB-A→Type-C 2]
```

**Павербанки** — чипси по потужності та БЗП.

Правила поведінки:

- фасети всередині одного ряду взаємовиключні (клік перемикає); ряди між собою
  комбінуються через `AND`; повторний клік знімає фільтр;
- список фасетів **виводиться з даних**, а не задається константою: додав товар
  із новою парою розʼємів — чипс зʼявився сам;
- **кожен ряд — один рядок із горизонтальним скролом**, без переносу. Висота
  передбачувана незалежно від кількості чипсів, товар не їде під згин екрана;
- на складі чипси з нульовим залишком **не ховаються** — «Type-C→Type-C · 0 шт»
  це і є сигнал до закупівлі. У POS такого чипса не буде фізично: каталог каси
  показує лише `stock > 0` (`usePOSCatalog.ts:22`);
- окремий чипс `Без характеристик · N` показується, коли в поточній категорії є
  товари з порожнім `specs` — інакше незаповнена позиція випадала б з усіх фасетів.

**Комплекти не змішуються з кабелями.** Фасет кабелів рахує тільки товари
категорії «Кабель»: інакше «7 шт Type-C→Type-C» перестає означати «7 кабелів на
полиці». Коли фасет кабелів дає `0 шт`, під ним підпис `у комплектах: 4` — сірим,
некликабельним, **тільки на складській сторінці**: у касі це продаж, а не закупівля.

## Рядок характеристик

Компактний рядок `formatSpec(specs)` під назвою:

```
USB-A→Type-C · 3A · 1м
PD30W+QC3.0 · USB-A, USB-C · + Type-C→Type-C
```

Показується в рядку таблиці складу, на картці POS і на картці вітрини `/shop`
(50 із 66 позицій видимі публічно, з них 31 — живлення). Назву не замінює,
йде під нею.

Назву й `specs` не синхронізуємо: назва — вільний текст постачальника. Але рядок
характеристик стоїть поряд із назвою, тож розбіжність («у назві 60W, у полі 100»)
видно оком.

## Структура коду

| Файл | Відповідальність |
|---|---|
| `src/lib/accessory-specs.ts` | типи, zod-схема, словники підписів, парсер назв, `parseSpecsFromFormData`, `formatSpec`, `buildFacets`, `matchesFacets` |
| `src/components/forms/AccessorySpecFields.tsx` | поля форми за категорією |
| `src/components/accessories/SpecFacets.tsx` | ряди чипсів + бейджі; спільний для складу й POS |
| `src/lib/actions/accessories.ts` | збирає `specs` із formData, валідує, пише в БД (create + update + import) |
| `src/app/admin/accessories/table.tsx` | стан фасетів, застосування фільтра, рядок характеристик |
| `src/app/admin/accessories/ImportAccessoriesButton.tsx` | розбір назв у прев'ю імпорту |
| `src/app/admin/sales/pos/usePOSCatalog.ts`, `POSCatalog.tsx` | фасети й рядок у касі |
| `src/app/shop/ShopContent.tsx` | рядок характеристик на вітрині |

`buildFacets` і `matchesFacets` — чисті функції над масивом товарів, без React.
Це дозволяє покрити їх тестами й використати в обох місцях без дублювання.

## Заповнення наявних 33 позицій

Разовий прогін того самого парсера → `UPDATE`. Розбір однозначний для 30 позицій
із 33. У трьох портів у назві немає взагалі:

| Позиція | Що робимо |
|---|---|
| `МЗП Hoco CS112A Lounge PD30W+QC3.0 + кабель Type-C to Type-C` | `ports: []` |
| `МЗП Hoco CS21A Rich QC3.0 18W + кабель USB to MicroUSB` | `ports: []` |
| `Power Bank Hoco J140A Tony ultra-thin PD20W з БЗП 5000 mAh` | `ports: []` |

**Не вгадуємо.** Порти можна було б вивести з протоколів (PD+QC3.0 → USB-A і
USB-C), але порти ні в якому фасеті не беруть участі — фільтри це пари розʼємів,
вати блоків і комплектність. Порожнє поле нічого не ламає, а в формі видно, що
там пусто. «Не заповнено, заповни з коробки» чесніше за «я вгадав, перевір».

## Порядок викату

Вітрина публічна, а прод у цьому проєкті єдиний. Тому дані стають видимими
клієнту тільки після того, як їх звірено:

1. Міграція `specs jsonb` — сама по собі нічого не змінює.
2. Деплой UI: форма, імпорт, чипси на складі, чипси й рядок у POS. **Вітрину не чіпаємо.**
3. Прогін парсера по 33 позиціях.
4. Користувач вичитує результат **на складській сторінці**, у звичному інтерфейсі.
5. Після підтвердження — рядок характеристик на вітрину, окремим деплоєм.

Ціна — два деплої замість одного. Натомість клієнт не бачить неперевірених
характеристик, а вичитка відбувається в UI, а не в таблиці в чаті.

## Тести

Vitest, поруч із наявними `__tests__`:

1. **Парсер назв:** усі 33 наявні назви → очікуваний `PowerSpec` (табличний тест;
   він же ловить регресію, якщо правила розбору поправлять).
2. Часткове розібрання: назва без довжини дає розʼєми і `length_m: undefined`.
3. `parseSpecsFromFormData` — кабель, блок, блок із комплектним кабелем, павербанк;
   порожні числові поля дають `undefined`, а не `0`; повністю порожня секція дає `null`.
4. zod відкидає `cable` без `from`/`to`, відʼємні числа, дублікати в `ports`.
5. Режим редагування: парсер не перезаписує вже заповнене поле.
6. `formatSpec` — усі три категорії плюс комплект.
7. `buildFacets` — бейдж рахує **суму `stock`**, а не кількість позицій; пари з
   нульовим залишком присутні; комплекти не потрапляють у фасети кабелів.
8. `matchesFacets` — `AND` між рядами, `OR` не виникає всередині ряду.

## Ризики

- **Верстку на телефоні перевірити неможливо** — розширення Chrome у цьому
  середовищі не підключається. Горизонтальний скрол чипсів і три ряди фільтрів
  у POS дивиться користувач.
- **Порти без кількості** — свідома втрата точності, див. модель.
- **Помилка в характеристиках потрапляє на публічну вітрину.** Пом'якшено
  порядком викату (розділ вище) — вітрина вмикається останньою, після вичитки.
