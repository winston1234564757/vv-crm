# Розширені характеристики аксесуарів живлення

**Дата:** 2026-08-09
**Статус:** затверджено до реалізації

## Задача

На складі 18 кабелів, 14 зарядних пристроїв і 1 павербанк. Усі суттєві
характеристики — розʼєм, потужність, комплектність — закодовані текстом усередині
`accessories.name`:

```
Кабель Hoco X96 Hyper Type-C to Type-C 100W (1m)
МЗП Borofone BA97A PD30W (1USB-C)
МЗП Hoco CS93A Leader PD20W (1USB-C) + кабель Type-C to Type-C
```

Через це на питання «скільки лишилось саме Type-C→Type-C» і «скільки блоків на
30 Вт» відповіді немає: фільтр працює лише по категорії (`cable`, `charger`, …),
пошук — підрядком по назві. Продавець за прилавком читає 18 назв очима.

Треба структуровані характеристики: заводяться руками у формі товару, показуються
фасетними фільтрами із залишками на сторінці «Аксесуари» та в POS.

## Обсяг

**Входить:** категорії `cable`, `charger`, `powerbank`.

**Не входить:**
- решта 5 категорій (`case`, `screen_protector`, `headphones`, `speaker`, `other`)
  — форма для них не змінюється;
- CSV-імпорт — колонок під характеристики не отримує, імпортований товар
  доповнюється руками;
- окремий екран-зведення по залишках.

## Модель даних

Одна колонка `specs jsonb` на `accessories` (nullable). Чому не окремі колонки:
`database.ts` у цьому проєкті не регенерується, тип пишемо руками в обох випадках;
даних 46 рядків, індекси не потрібні; а комплект «блок + кабель в одному SKU» у
колонковій схемі дав би два майже дублюючі набори полів.

```ts
// src/lib/accessory-specs.ts
type Connector = "usb_a" | "usb_c" | "lightning" | "micro_usb";
type Port      = "usb_a" | "usb_c";           // вихід блока/павербанка
type Protocol  = "pd" | "qc3";

type CableSpec = {
  from: Connector;
  to: Connector;
  watts?: number;      // як на коробці
  amps?: number;       // як на коробці
  length_m?: number;
};

type ChargerSpec = {
  watts?: number;
  protocols: Protocol[];
  ports: Port[];       // перелік типів без кількості
};

type PowerbankSpec = {
  mah?: number;
  watts?: number;
  wireless: boolean;
  ports: Port[];
};

type PowerSpec = {
  cable?: CableSpec;
  charger?: ChargerSpec;
  powerbank?: PowerbankSpec;
};
```

**Комплект не має власного типу.** Комплект — це запис, де присутні одночасно
`charger` (або `powerbank`) і `cable`. Тому набір полів кабеля один на всі випадки,
без дублювання.

Вати й ампери — два незалежні необовʼязкові поля; заповнюється те, що надруковане
на упаковці. Ніяких перерахунків 2.4A → 12Вт: цифра в картці має збігатися з тим,
що клієнт бачить на коробці.

Порти — перелік типів без кількості: `["usb_a", "usb_c"]`. Наслідок, прийнятий
свідомо: блок з двома USB-A не відрізнити від блока з одним.

### Валідація

`specs` розбирається zod-схемою (zod 4 вже в залежностях) на кожному записі.
Без цього друкарська помилка в ключі jsonb пройде мовчки, а товар просто зникне
з фасета — помилка, яку майже неможливо помітити.

Правила:
- `cable.from` / `cable.to` — обовʼязкові, якщо блок `cable` присутній;
- `charger.ports`, `powerbank.ports` — масиви без дублікатів, можуть бути порожні;
- числові поля — додатні; порожній рядок із форми стає `undefined`, а не `0`;
- порожній `PowerSpec` (жодного блока) зберігається як `null`, не як `{}`.

### Міграція

```sql
alter table accessories add column specs jsonb;
```

`database.ts` не регенеруємо — тип додається вручну до інтерфейсу рядка
`accessories`, доступ у місцях, де згенерований тип не знає про колонку, через
`as any` (усталена практика проєкту).

## Форма товару

У `AccessoryForm` додається секція «Характеристики», видима залежно від обраної
категорії:

| Категорія | Поля |
|---|---|
| Кабель | Звідки → Куди (2 селекти), Вт, A, довжина (м) |
| Зарядний пристрій | Вт, протоколи (чекбокси PD / QC3.0), порти (чекбокси USB-A / USB-C), тумблер «У комплекті кабель» → розкриває поля кабеля |
| Павербанк | mAh, Вт, БЗП (чекбокс), порти, той самий тумблер |
| решта | секція не показується |

Перемикання категорії в селекті перемальовує секцію без втрати вже введених
значень інших блоків (стан секції живе в React, у formData їде лише актуальне).

Поля виносяться в окремий компонент `src/components/forms/AccessorySpecFields.tsx` —
`AccessoryForm` уже 200 рядків, вбудовування трьох наборів полів зробило б його
нечитним.

## Фільтри

Другий ряд чипсів під наявним рядом категорій. Показується лише коли обрано
категорію живлення. Бейдж на чипсі — **штуки** (`sum(stock)`), не позиції: питання
було «скільки залишилось».

Чипси з нульовим залишком **не ховаються** — «Type-C→Type-C · 0 шт» це і є сигнал
до закупівлі.

**Кабелі** — чипси по парах розʼємів, зібрані з наявних даних:

```
[USB-A→Type-C 5 шт] [Type-C→Type-C 7 шт] [USB-A→microUSB 6 шт] [Type-C→Lightning 4 шт]
```

**Блоки** — два ряди:

```
Потужність:   [18W 3] [20W 6] [22.5W 2] [30W 7]
Комплект:     [Тільки блок 11] [+ Type-C→Type-C 4] [+ Type-C→Lightning 2] [+ USB-A→Type-C 2]
```

**Павербанки** — чипси по потужності та БЗП.

Фасети всередині одного ряду взаємовиключні (клік перемикає); ряди між собою
комбінуються через `AND`. Повторний клік по активному чипсу знімає фільтр.

Список фасетів **виводиться з даних**, а не задається константою: додав товар із
новою парою розʼємів — чипс зʼявився сам.

Окремий чипс `Без характеристик · N` показується, коли в поточній категорії є
товари з порожнім `specs`. Без нього незаповнена позиція випадала б з усіх фасетів
і зникала б зі складу для користувача — а заповнення ручне, тож такі позиції будуть.

У рядку таблиці та на картці POS додається компактний рядок характеристик:
`USB-A→Type-C · 3A · 1м`, `PD30W+QC3.0 · USB-A, USB-C · + Type-C→Type-C`.

## Структура коду

| Файл | Відповідальність |
|---|---|
| `src/lib/accessory-specs.ts` | типи, zod-схема, словники підписів, `parseSpecsFromFormData`, `formatSpec`, `buildFacets`, `matchesFacets` |
| `src/components/forms/AccessorySpecFields.tsx` | поля форми за категорією |
| `src/components/accessories/SpecFacets.tsx` | ряди чипсів + бейджі; спільний для сторінки й POS |
| `src/lib/actions/accessories.ts` | збирає `specs` із formData, валідує, пише в БД (create + update) |
| `src/app/admin/accessories/table.tsx` | стан фасетів, застосування фільтра, рядок характеристик |
| `src/app/admin/sales/pos/usePOSCatalog.ts`, `POSCatalog.tsx` | те саме в касі |

`buildFacets` і `matchesFacets` — чисті функції над масивом товарів, без React.
Це дозволяє покрити їх тестами й використати в обох місцях без дублювання.

## Заповнення наявних 33 позицій

Одноразовий розбір назв → `UPDATE`. Назви дисципліновані, розбір однозначний для
30 позицій із 33. Три потребують здогадки:

| Позиція | Що домислюється |
|---|---|
| `МЗП Hoco CS112A Lounge PD30W+QC3.0 + кабель Type-C to Type-C` | портів у назві немає; з протоколів виводимо `["usb_a","usb_c"]` |
| `МЗП Hoco CS21A Rich QC3.0 18W + кабель USB to MicroUSB` | портів у назві немає; виводимо `["usb_a"]` |
| `Power Bank Hoco J140A Tony ultra-thin PD20W з БЗП 5000 mAh` | портів у назві немає; лишаємо `[]` |

Ці три не заповнюються мовчки — після заливки виводиться список позицій, де
значення виведене, а не прочитане, і користувач звіряє з коробкою. Візуальна
перевірка в цьому проєкті — робота користувача, тож приховувати здогадки не можна.

Правила розбору (для скрипта):
- `USB to X` → `from: usb_a`; `Type-C to X` → `from: usb_c`;
- `MicroUSB` → `micro_usb`, `Type-C` → `usb_c`, `Lightning` → `lightning`;
- `\d+(\.\d+)?W` → `watts`, `\d+(\.\d+)?A` → `amps`, `\((\d+(\.\d+)?)m\)` → `length_m`;
- `PD` → протокол `pd`, `QC3.0` → `qc3`;
- `(1USB-A/1C)` → `["usb_a","usb_c"]`, `(1USB-C)` → `["usb_c"]`, `(1USB-A)` → `["usb_a"]`;
- `+ кабель X to Y` у назві блока → блок `cable` із тими самими правилами;
- `з БЗП` → `wireless: true`, `\d+ mAh` → `mah`.

Скрипт розбору живе в репозиторії (`scripts/`), а не існує лише в історії чату:
партія товару приходить регулярно, і той самий розбір знадобиться знову.

## Тести

Vitest, поруч із наявними `__tests__`:

1. `parseSpecsFromFormData` — кабель, блок, блок із комплектним кабелем, павербанк;
   порожні числові поля дають `undefined`, а не `0`; повністю порожня секція дає `null`.
2. zod відкидає `cable` без `from`/`to`, відʼємні числа, дублікати в `ports`.
3. `formatSpec` — усі три категорії плюс комплект.
4. `buildFacets` — бейдж рахує **суму `stock`**, а не кількість позицій; пари з
   нульовим залишком присутні в списку.
5. `matchesFacets` — `AND` між рядами, `OR` не виникає всередині ряду.
6. Розбір назв: усі 33 наявні назви → очікувані `PowerSpec` (табличний тест;
   він же ловить регресію, якщо правила розбору поправлять).

## Ризики

- **Дані вводяться руками, тож будуть неповні.** Товар без `specs` не потрапляє
  в жоден чипс. Щоб він не зник із очей, при активному фасеті показуємо лічильник
  «без характеристик: N» — інакше позиція просто випаде зі складу для користувача.
- **Порти без кількості** — свідома втрата точності, див. вище.
- **Назва й `specs` можуть розійтися:** назва каже «60W», у полі стоїть 100. Синхронізацію
  не робимо (назва — вільний текст постачальника), але рядок характеристик показується
  поряд із назвою в таблиці, тож розбіжність видно оком.
