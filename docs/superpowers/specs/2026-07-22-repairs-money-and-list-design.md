# Ремонти: закрити контур грошей і переставити список на сегменти

Дизайн слайсу 2 редизайну vv-crm. Узгоджено 2026-07-22.

## Головне, що знайшов брейншторм

**Виторг із ремонтів не потрапляє у фінанси взагалі.**

- У `transactions` немає жодного рядка `reference_type = 'repair_payment'`.
  Наявні типи: `sale`, `distribution`, `device`, `expense`, `part`,
  `inventory`, `top_up`.
- `repairs.payment_status` пишеться лише при прийомі
  (`lib/actions/repairs.ts:414,443`) і редагується вручну через
  `EditRepairForm.tsx:321`. Це **зміна підпису на рядку**: транзакції немає,
  каса не змінюється.
- `FinanceTransactionsTable.tsx:166,195,327` уже має готові гілки під
  `repair_payment`. Фінансова сторінка чекає на рядки, яких ніхто не створює.
- У базі є **«Каса ремонтів»** (`cash_registers.type='repairs'`) з балансом
  100 ₴ — касу завели, гроші в неї не течуть.

На живих даних: ремонт Redmi Note 13 за 1800 ₴ має `status='handed_over'` —
апарат віддано — і `payment_status='unpaid'`. Гроші не існують ніде.

Сервісний напрямок стартував 2026-07-18. Дві заявки. Закрити контур зараз
коштує двох записів; через півроку це міграція.

## Дизайн

### 1. `pay_repair` — оплата рухає гроші

Нова функція, `SECURITY DEFINER`, у стилі наявної `top_up_safe`:

```
pay_repair(p_repair_id uuid, p_cash_register_id uuid,
           p_amount integer, p_user_id uuid) returns void
```

1. Валідація: `p_amount > 0`; ремонт існує; каса існує; сума вже сплаченого
   плюс `p_amount` не перевищує `repairs.price`.
2. `UPDATE cash_registers SET balance = balance + p_amount`.
3. `INSERT INTO transactions` — `from_type='customer'`,
   `to_type='cash_register'`, `to_id=p_cash_register_id`,
   `reference_type='repair_payment'`, `reference_id=p_repair_id`.
   Схема збігається з тим, як записується продаж клієнту.
4. `payment_status` **перераховується з реєстру**, не встановлюється на віру:
   `paid`, якщо сума платежів ≥ ціни, інакше `partial`.

Реєстр стає джерелом правди, `payment_status` — кешем. Часткові оплати
працюють без нової колонки.

`REVOKE EXECUTE ... FROM PUBLIC, anon` одразу після створення: анонімний ключ
їде в браузерному бандлі, і в handoff §2 це вже одного разу пропустили для
30 функцій.

**Міграція пишеться і у файл `supabase/migrations/`**, не лише застосовується
через MCP — MCP локального файлу не створює (handoff §4).

Поверх неї — серверна дія `payRepair` і читання `getRepairPayments` для
історії платежів у драверу.

### 2. Форма сторінки

`PageHeader` + `StatCard` ×4 · сегменти в URL · `ListPageShell`.

Сегменти — **групи життєвого циклу**, не всі вісім статусів:

| Сегмент | Статуси |
|---|---|
| Усі | — |
| В роботі | received, diagnostics, in_progress, awaiting_parts |
| Готові | ready |
| Завершені | completed, handed_over |
| Скасовані | cancelled |
| **Борг** | не оплачено, не гарантія, ціна > 0 |

Точний статус — окремим `Select` у тулбарі, як тип/бренд на Техніці.
«Борг» — аналог «Потребує уваги» з Техніки: з'являється лише коли не
порожній. Зараз там був би один запис.

Це скасовує записане рішення handoff §4 («канбан лишається, перемикач —
іконковий сегментований контрол»). Слайс 1 уже скасував його половину для
Техніки; тепер застосунок має один шаблон сторінки-списку.

### 3. Кнопка наступного кроку

Найкраще з канбану (`RepairsKanban.tsx:60-66`) переїжджає в рядок:
`Прийнято → Діагностика → В роботу → Готовий → Видати`.

Перехід у «Видано» при несплаченому ремонті **питає підтвердження, але не
блокує**: гарантійні ремонти безкоштовні, клієнт може доплатити пізніше.
Саме цей сценарій уже стався один раз.

### 4. Мертвий вимір прибирається

`repair_type` не існує в базі; `data-repairs.ts:82` жорстко проставляє
`"customer"` кожному рядку. Через це фільтр «Складські» не може дати нічого,
бейдж завжди каже «Клієнт», а гілка `repair_type === "internal"` у канбані —
мертвий код. Прибирається з типів, фільтрів, бейджів і з мапінгу.

### 5. Нова чиста логіка

`src/lib/repair-flow.ts` — наступний крок, групи циклу, предикат боргу.
З тестами, як `lib/device-stage.ts`.

## Межа обсягу — свідома

**`RepairForm.tsx` (678 р.) не входить у цей слайс.** План ставив його сюди,
але слайс уже містить міграцію над грошима, і змішувати це з переробкою форми
на 20 полів в одному комміті — погана ідея для відкату.

Дані окремо підтверджують, що форма варта власного слайсу: обидва реальні
прийоми заповнили близько восьми полів із двадцяти, а `issue_nodes`,
`issue_diagnostics`, `is_external_sc`, `np_ttn`, `partner_id`, `is_warranty`,
`device_password`, `diagnosis_result`, `technician_notes_internal` — нулі на
всіх записах.

`RepairDetailView.tsx` (912 р.) чіпається точково — блок оплати з історією
платежів і статуси через `domain-labels`. Без повного перефарбування.

## Чого НЕ робимо

- Не додаємо колонку `paid_amount` — сума платежів рахується з реєстру.
- Не міняємо `createRepair` і прийом заявки.
- Не чіпаємо складські ремонти: вони належать Техніці (слайс 1), і
  виключення `.is("inventory_device_id", null)` лишається.
- Не блокуємо видачу неоплаченого ремонту.
