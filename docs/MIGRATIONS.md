# Міграції: як не розсинхронити репо з продом

## Правило

Supabase CLI на цій машині падає з segfault, тому весь DDL іде через MCP
`apply_migration`. У нього є пастка:

> **`apply_migration` ігнорує ім'я твого файлу і ставить власний штамп —
> поточний час виклику.**

Передаєш `name: "revoke_anon_execute_all_secdef"` — прод записує версію
`20260804162948`. Файл, який ти щойно назвав `20260805090000_...`, у проді
не існує. Наступного разу ніхто цього не помітить, бо все працює.

## Порядок дій

1. Викликати `apply_migration`.
2. **Одразу** викликати `list_migrations` і прочитати версію, яку прод справді записав.
3. Перейменувати локальний `.sql` під цю версію.
4. Закомітити файл.

Крок 2–3 пропускати не можна. Саме через це станом на 04.08.2026 у репо було
**35 файлів без жодного запису в проді** і **6 версій у проді без файлів** —
розрив на три тижні роботи. `supabase db push` на такому стані спробував би
переграти вже застосоване.

## Як звірити стан

```sql
-- має дати 0 і 0
with files(v) as (values ('...'), ('...'))   -- префікси всіх файлів
select
  (select count(*) from files f
    where not exists (select 1 from supabase_migrations.schema_migrations m where m.version=f.v))
    as files_without_tracking,
  (select count(*) from supabase_migrations.schema_migrations m
    where not exists (select 1 from files f where f.v=m.version))
    as tracking_without_files;
```

Список префіксів:
```powershell
Get-ChildItem supabase/migrations/*.sql |
  ForEach-Object { $_.Name -replace '^(\d+)_.*$','$1' } | Sort-Object -Unique
```

## Що зробили 04.08.2026

Реєстр зведено: 100 файлів ↔ 100 записів, обидва боки діфу нульові.

- `20260727160000_withdraw_share_only_from_net_profit_safe.sql` →
  `20260727160500_...`. Два файли ділили один префікс, а Supabase ключується
  саме по ньому — один із них міг мовчки не застосуватись на чистому деплої.
- Створено `20260729115900_transactions_payment_method.sql`: колонка була в
  проді без жодної міграції, хоча вся серія `20260729120x` на неї спирається.
  Чистий деплой падав би на першій же з них.
- Шість «сиріт» (`20260803083834`, `20260803084339`, `20260803084933`,
  `20260803090959`, `20260803092615`, `20260804130535`) **перейменовано, не
  видалено** — це ті самі міграції, що файли, під штампом `apply_migration`.
  UPDATE версії зберігає записані `statements`; delete+insert їх би втратив.
- Дозаповнено 29 решти застосованих, але не облікованих.

## Дрібниця, яка колись зекономить годину

Звірку робити через `execute_sql`, а не `apply_migration` — інакше сама звірка
додасть у таблицю ще один рядок і зіпсує те, що щойно звели.
