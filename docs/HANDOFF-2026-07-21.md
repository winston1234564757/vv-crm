# Handoff — UX redesign session, 2026-07-21

State of the vv-crm UX/design overhaul and everything still open. Read this
before continuing; it exists so the next session does not redo finished work or
re-derive the traps.

---

## 1. OPEN — start here

### 1.1 Open self-registration — ONE STEP LEFT, and it is the owner's

**Investigated and mostly resolved. The remaining step cannot be done from code.**

The earlier framing of this item ("11 always-true policies grant everyone
access") was wrong in its diagnosis. Every one of the 11 flagged policies is
scoped to the `authenticated` role, which for a five-person shop is a defensible
design. The actual hole was the door in front of them:

1. `/login` shipped a public "Створити акаунт" signup form.
2. The `handle_new_user` trigger on `auth.users` auto-assigned `role = 'sales'`.
3. Email confirmation is off — every account has `email_confirmed_at` set ~40 ms
   after `created_at`, so signup returned a live session immediately.

A stranger could register and instantly hold full SELECT/INSERT/UPDATE on
`customers` (names, phones), `sales`, `repairs`, `devices` and `partners`. There
is no app-level backstop: no role check in middleware, only three scattered
`role ===` checks in the whole codebase.

Done: signup UI removed from `src/app/login/page.tsx`; `partners` DELETE
tightened to owner/manager (migration `20260721142241`); the three stale test
accounts (`test_audit@`, `test_antigravity@`, `qa_tester@`) deleted — they owned
zero rows, and every FK to `profiles` is `ON DELETE SET NULL`, so nothing
cascaded.

**STILL OPEN — owner action, dashboard only:** Authentication → Sign In /
Providers → disable **"Allow new users to sign up"**. Removing the form is
cosmetic on its own: the anon key ships in the browser bundle, so anyone can
POST straight to `/auth/v1/signup` regardless of the UI. There is no MCP tool
that reaches auth config.

The remaining `USING (true)` policies were left in place deliberately — see §4.

### 1.2 Visual QA of server-side pagination on Sales

`/admin/sales` was rewritten to server-side pagination and **was never seen in a
browser**. Verify: search (debounced 350 ms), both filters, period switcher,
page navigation, page-size selector. Everything is URL-driven — `?q=&cat=&pay=&page=&size=&period=`.

### 1.3 ~~Regenerate `src/types/database.ts`~~ — DONE 2026-07-22

The `callRpc` wrapper is gone; both calls are plain typed `.rpc()`.

Not regenerated wholesale — measured first. All 28 tables matched the live
schema on column counts, `sales` already carried `status` / `is_warranty`, and
the `sale_type` enum already matched, so the file was stale by *exactly* two
functions. A full regeneration would have round-tripped ~30 k tokens to add ~18
lines, so `sales_analytics` and `search_sales_ids` were appended by hand in the
generator's own style and position (alphabetical). `tsc --noEmit` and
`npm run build` both pass.

Two traps if you touch this file again:

- **It is UTF-16LE with CRLF**, not UTF-8. `Read`/`Edit` see the raw bytes and
  will mangle it; patch it with a script that does
  `readFileSync().toString("utf16le")` and writes the BOM back.
- **All args of both functions have SQL defaults**, so the generated `Args` mark
  them optional (`p_query?: string`). Pass `undefined`, never `null`, for an
  absent filter — the text defaults are `NULL` so the semantics match, but the
  optional type rejects `null`.

Still worth a real `supabase gen types` run once the CLI works here; the hand
edit is correct but the file no longer has a machine-verified provenance.

### 1.4 Smaller security items still open

- **`crm_media` is a public bucket whose SELECT policy allows *listing*** every
  object, not just fetching a known URL. Public buckets do not need this.
- **Money-perimeter inconsistency.** `safes` and `transactions` SELECT are gated
  to owner/manager, but `expenses`, `purchases`, `cash_registers`,
  `payment_splits` and `inventory_movements` are `ALL` for any authenticated
  user — a `sales` account can write them. Deliberately not changed: unclear
  whether sales staff legitimately record expenses or goods receipts, and
  guessing would lock them out. Ask the owner first.
- **6 `anon`-executable SECURITY DEFINER functions remain** after the revoke in
  §2. All six are trigger functions (`handle_new_user`,
  `update_partner_balance_on_sale`, …) and Postgres refuses to invoke those over
  RPC, so this is hygiene, not exposure. The revoke migration skips them on
  purpose (`prorettype <> 'trigger'::regtype`).
- 32 `function_search_path_mutable` warnings — untouched.

### 1.5 Lower priority

- Receipt/print components and the public `tracker` / `shop` / `track` pages are
  still on the old palette. **Deliberate:** receipts need literal colours because
  thermal printing and `html-to-image` do not resolve CSS variables reliably.
- Other admin lists still use client-side pagination. That is fine — see §4.

## 2. Shipped this session

**Design system** — light theme, teal accent, semantic OKLCH tokens in
`src/app/globals.css`. Legacy names (`--color-violet`, `--color-warm-*`, …) are
kept as aliases with identical values so un-migrated markup still works; do not
add new usages. Fonts: Space Grotesk (display) + Hanken Grotesk (body).
`DESIGN.md` describes the system.

**Primitives** in `src/components/ui/`: `Button`, `Tabs`, `Badge`, `StatCard`,
`Pagination` (+ `usePagination`).

**Navigation** — `src/lib/nav-config.ts` is the single source of truth. Five
domain groups plus standalone Dashboard / Settings / Store-launch; grouped
sidebar, config-driven mobile nav, route-based `SectionTabs` mounted once in
`admin/layout.tsx`.

**Pages** — dashboard regrouped into named sections; Sales gained period
selector, trend chart and breakdowns; every admin list is paginated.

**Sales server-side pagination** — two SECURITY INVOKER Postgres functions
(`search_sales_ids`, `sales_analytics`) plus `getSalesPage` / `getSalesAnalytics`
in `src/lib/data-sales.ts`.

### Pre-existing bugs found and fixed

- **React #300 on repair save.** Four `useState` calls sat after the
  `if (createdData) return …` early return in `RepairForm.tsx`, so the hook count
  shrank the moment a repair was created. The repair saved, the UI crashed.
- **`anon` could execute 30 SECURITY DEFINER functions** — including
  `transfer_funds`, `delete_sale`, `refund_sale`, `top_up_safe`. Postgres grants
  EXECUTE to PUBLIC by default and `anon` inherits it; the anon key ships in the
  browser bundle. Revoked from PUBLIC/anon, re-granted to authenticated and
  service_role. **Money flows should be re-tested on production.**
- Non-deterministic builds (see §3), a broken `dev` script, an invisible
  white-on-white button on the repairs mobile island, and a wrong `AccessoryRow`
  type that `ignoreBuildErrors` had been hiding.

## 3. Traps — read before building or deploying

**Builds were a lottery, and the first diagnosis was wrong.** Switching
`hashFunction` md4 → sha256 only changed the error text; both md4 and xxhash64
are WASM-backed in webpack. The real cause is webpack's persistent filesystem
cache feeding `undefined` to the hasher after a large change set — surfacing as
`Cannot read properties of undefined (reading 'length')` or
`ERR_INVALID_ARG_TYPE`. `config.cache` is now disabled for production builds
only (dev keeps its cache). Do not re-enable it.

**`typescript.ignoreBuildErrors` was removed.** A type error now fails the
build. If one appears, fix the type — do not restore the flag; that flag is what
let the broken `AccessoryRow` reach production.

**`npm run dev` needs `--webpack`** (already in package.json). Next 16 defaults
to Turbopack while this project has a webpack config.

**Deploy:** commit to `master`, push, then `npx vercel --prod --yes`. The CLI is
authenticated and the project is linked. A network `ECONNRESET` during status
polling does not mean the deploy failed — check with
`npx vercel inspect <deployment-id>` before retrying.

**Claude-in-Chrome never connected** in this session, so nothing was visually
verified. `tsc` and `next build` catch nothing visual — two of the bugs above
surfaced only when the owner used the app. State plainly what was not seen and
ask him to look.

## 4. Decisions worth not re-litigating

- **The remaining `USING (true)` policies stay.** With self-registration closed,
  "any authenticated user" means one of five known staff accounts. The owner
  chose the minimal change over a full role-aware rewrite: sales staff genuinely
  need to create and edit customers, sales, repairs and devices, and tightening
  those would break daily work to satisfy an advisor warning. The advisor will
  keep reporting ~8 `rls_policy_always_true` findings. That is expected.
- **Migrations must be written to `supabase/migrations/` as well as applied.**
  Four migrations existed only in the remote DB and were recovered from
  `supabase_migrations.schema_migrations`. Applying via MCP does not create the
  local file; write it by hand, named with the same version the remote recorded.
- **Server-side pagination is premature for the other lists.** Measured volumes:
  accessories 40, devices 26, repairs 15, sales 8, everything else under 6 — about
  114 rows total. Sales was converted anyway at the owner's explicit request after
  seeing those numbers. Revisit when `sales` passes roughly 2000–3000 rows; it
  grows fastest and carries nested items and payments.
- **Kanban views are not paginated** (repairs, devices) — they are grouped by
  status and slicing them into pages breaks the mental model.
- **"Select all" is page-scoped** in repairs and parts, so a checkbox can never
  select rows the user cannot see.
- **The repairs board/list toggle stays an icon segmented control**, not `Tabs`.
- **`AddDistributionButton` keeps its soft `bg-violet/10` styling** — no matching
  `Button` variant, and flattening it to primary would change the finance page's
  visual hierarchy.
- **~200 remaining `bg-violet` occurrences are mostly tints** (`/5`, `/10`) for
  badges and highlights, not CTAs. Do not sweep them blindly.
